> **2026-09-02: COMET ABANDONED — every "Comet" below now means CHROME (the default browser). See [[feedback-browser-chrome-default]].**

Official `telegram@claude-plugins-official` plugin (the "channel" bridge, distinct from the homemade [[reference_tg_bridge]] and tg-terminal). State dir: `~/.claude/channels/telegram/` (`.env` holds `TELEGRAM_BOT_TOKEN`, `access.json` holds dmPolicy/allowFrom/pending, `bot.pid`). Server = `bun server.ts` long-poller spawned per session via `.mcp.json`.

**Two non-obvious rules that cost hours on 2026-06-21:**

1. **Inbound only reaches a session launched with `claude --channels plugin:telegram@claude-plugins-official`.** A plain `claude` or `claude --resume` loads the plugin's TOOLS (reply/react) but the session is NOT subscribed — Claude Code logs `Channel notifications skipped: ... not in --channels list for this session` and drops every incoming DM. Outbound replies still work (direct Telegram send), which masks the problem. The flag is per-launch; `/mcp` reconnect does NOT add it.

2. **EVERY Claude session with this plugin enabled spawns a `server.ts` poller — even a plain `claude` with NO `--channels`, and the LAST session to start STEALS the bot token.** Telegram allows one `getUpdates` consumer per token; `server.ts` kills the previous holder before it begins polling (the `bot.pid` stale-killer, server.ts:56-69), so the newest poller wins. **PROVEN 2026-06-21 (this is THE reason the working bot dies "the moment you fire up another session"):** session `f9aaa6e1` launched WITH `--channels` was live, `polling as @Claudio_al_TG_v2_bot`, and replying to the user's DMs. The user then opened a second, UNRELATED plain session `3945b48c` (its log says `Channel notifications skipped … not in --channels list`) — yet it still booted a poller, killed f9aaa6e1's poller, and seized `bot.pid`. Because the thief was NOT subscribed, every inbound DM was polled-and-dropped and the working session went silent. **CORRECTION of a tempting-but-FALSE belief (the bot asserted this to the user and was wrong): a "non-telegram" second session is NOT safe — the plugin's MCP server boots in every session, so it still polls and still steals the token.** Practical rule: the `--channels` session must be the LAST claude you start, and don't open another claude afterward. Recovery if hijacked: `/mcp` reconnect (or restart) the `--channels` session so its `server.ts` re-acquires the token. Different bot = different token = never conflicts (scale via a separate @BotFather bot per session).

   **REFINEMENT — CONFIRMED 2026-06-21 by live A/B test (with the user):** the token theft is triggered by a poller **(RE)STARTING**, NOT by a sibling session merely existing or being chatted in. Test: the `--channels` bridge was live; the user actively typed a prompt into the very session that had earlier killed it — the bridge KEPT replying. So an idle/working sibling claude session is HARMLESS; only a fresh launch, a relaunch, or an `/mcp` reconnect in another session respawns its poller and snatches `bot.pid`. Livable rule: you CAN keep and use other claude sessions alongside the bridge — just keep the `--channels` session the LAST one to (re)start its MCP, and don't run `/mcp` reconnect or relaunch claude in the other sessions while the bridge is live. If one does steal the token, `/mcp` reconnect in the `--channels` session reclaims it (proven this session).

**STABILIZATION via tokenless state dir (built + proven 2026-06-21):** the disconnect war (rule 2) is solved by making every NON-savior session inert. `server.ts:26` reads `STATE_DIR` from `process.env.TELEGRAM_STATE_DIR` (verified: Claude Code forwards arbitrary shell env vars to plugin MCP servers — same path that leaked the token), and `server.ts:45-52` **exits before writing `bot.pid`/running the stale-killer if no token is found**. So: (a) `~/.claude/channels/telegram-null/` = empty dir, NO `.env`; (b) the PowerShell profile defaults `TELEGRAM_STATE_DIR` → that null dir for every shell `if (-not $env:TELEGRAM_STATE_DIR)`; (c) `~/.claude/scripts/start-savior.ps1` overrides it with the REAL dir (`~/.claude/channels/telegram`) + `--channels` to launch the one savior. Result: ordinary work sessions find no token → poller exits → never spawn a competitor → can't kill the savior. PROVEN by A/B: clean shell (no stray `TELEGRAM_BOT_TOKEN`) + null dir → no `bot.pid` written; stray token present → poller spawns. CAVEAT: the null trick needs the ambient env free of `TELEGRAM_BOT_TOKEN` (the profile guard ensures this for fresh terminals); even with a stray token it still protects the savior IF that token ≠ the savior's (separate dir + separate token = no kill, no 409). **AGENTS/subagents do NOT count** — they run inside a session, share its MCP connection, and spawn NO new poller; only top-level `claude` processes do. So unlimited agents + the auto-inert default = scales to any number of daily work sessions; only the 1-2 bot sessions need a dedicated launcher. In work sessions the telegram MCP shows "failed/disconnected" — intended (no poller).

**Token lives in TWO files (keep in sync):** canonical = `~/.claude/channels/telegram/.env` as `TELEGRAM_BOT_TOKEN` (what `server.ts` reads); copy = `~/.env/telegram-channel.env` as `TELEGRAM_CHANNEL_BOT_TOKEN`. There is NO `~/.env/telegram.env`. For diagnostics read the canonical channels `.env`.

**The env-leak bug that cost the afternoon of 2026-06-21 (3rd non-obvious rule):** `server.ts` does **"real env wins"** — it only loads `channels/telegram/.env` if `process.env.TELEGRAM_BOT_TOKEN` is *undefined* (server.ts:31-38). The PowerShell profile auto-loads every `~/.env/*.env` into the shell, and FOUR homemade bots (sodanotif/sodaos/tg-bridge/tg-terminal) each defined the SAME var `TELEGRAM_BOT_TOKEN`; the alphabetically-last (`tg-terminal.env` = a dead/401 token `8596413380`) won the global, leaked into the plugin process, and the channel server polled the wrong bot → user's DMs piled up unconsumed, no replies. SYMPTOM: `getWebhookInfo` shows pending drains to 0 (polling works) yet no reply ever arrives, and the MCP log shows `deleteWebhook 401 Unauthorized`. FIX (applied 2026-06-21): each homemade bot's env key renamed to a unique name (`TG_BRIDGE_BOT_TOKEN`, `TG_TERMINAL_BOT_TOKEN`, `SODAOS_BOT_TOKEN`, `SODANOTIF_BOT_TOKEN`) + readers updated; AND the profile loader now hard-skips promoting the bare `TELEGRAM_BOT_TOKEN` to the global shell (guard in `Microsoft.PowerShell_profile.ps1`). So the plugin always falls back to its own `channels/.env`. Takes effect only in a FRESH terminal (the running session keeps the baked-in stale value until `claude` is relaunched).

**Diagnostics (non-destructive):** `getWebhookInfo` (`https://api.telegram.org/bot<token>/getWebhookInfo`) shows `pending_update_count` WITHOUT competing with the poller. Healthy = empty `url` (long-polling, no webhook), `pending_update_count` ~0, no `last_error_message`; a `409` here = the per-dir poller war. NEVER call `getUpdates` manually to debug — it IS a competing consumer and breaks the live poller (tips it past the 8×409 give-up guard in server.ts:1023). Claude Code's own MCP debug log: `%LOCALAPPDATA%\claude-cli-nodejs\Cache\C--Users-Alessandro\mcp-logs-plugin-telegram-telegram\*.jsonl`.

**Clean setup:** plain `claude` → `/plugin install telegram@claude-plugins-official` + `/reload-plugins` → `/telegram:configure <token>` → quit → relaunch with `--channels` flag → DM bot plain text → `/telegram:access pair <code>` → `/telegram:access policy allowlist`. Pairing/allowlist mutations are operator-terminal-only, never from a channel message (prompt-injection guard).

**4th non-obvious rule — `claude -p` CHILDREN INHERIT `TELEGRAM_STATE_DIR` (root cause of the 2026-07-18 outage, found + fixed same day):** every `claude -p` (headless) also boots the plugin's server.ts poller. Tool-call shells INSIDE the savior session carry `TELEGRAM_STATE_DIR=telegram-v3` (start-savior2 set it; the profile guard keeps existing values), so ANY daemon/script started from the savior session passes the V3 dir to its `claude -p` children → each classify spawn steals the savior's getUpdates → savior 409-dies (~8 min give-up), and the transient child deletes bot.pid on exit. THAT is how restarting sodanotif `daemon.js` from the savior session at 17:13 serial-killed every savior poller (deaths 17:14/17:22/18:2x; bot.pid deletion 18:06:29 = the 16:06:30Z flush's child exiting). Conversely, SCHEDULED scripts run profile-less → var UNSET → plugin defaults to the OLD `channels/telegram` dir (v2 token) → stray v2 pollers every run. **STANDING FIX: every script that spawns `claude -p` (or a daemon that does) must hard-set `TELEGRAM_STATE_DIR` to the tokenless `telegram-null` dir.** Applied 2026-07-18 to sodanotif `start-daemon.ps1`, `watch.ps1`, `recap.ps1`. When writing ANY new claude-p-spawning automation, add the same line — and never start daemons from the savior session without it.

Proven: the Quick Claude panel launched by an AHK that had been reloaded from the savior session killed poller 1868 at 01:59 ("replacing stale poller", then polled-and-DROPPED messages, then died with its window). RECOVERY findings (same night): once this session's plugin shows "disconnected", ToolSearch returns no match for its tools and ListMcpResourcesTool does NOT respawn it — there is NO self-service reconnect from inside; only the USER's `/mcp` (or restart) does it.

**Buttons — TESTED 2026-06-22 (settled, don't re-litigate):**
- **Inline URL buttons WORK** (`inline_keyboard` with `url`) — tap opens the link in the default browser (Comet). CONFIRMED live by the user. This is the "open the chat" shortcut: a 🔗 Open button per notification item (wa.me/<number> for WA DM, web.whatsapp.com for WA group, Gmail thread URL, Slack permalink). No handler/plumbing needed.
- **Custom inline CALLBACK buttons** render and the tap IS received (plugin `bot.on('callback_query:data')`, server.ts:731) BUT the handler ONLY acts on its own `perm:(allow|deny|more):<id>` data and silently `answerCallbackQuery()`s everything else → arbitrary callback buttons do nothing. (msg 38: rendered, tap ignored.)
- **Reply-keyboard buttons did NOT render** on the user's phone OR desktop (msgs 41/42, even `is_persistent`) — dead end.
- **Incoming REACTIONS are NOT received** — no `message_reaction` handler in server.ts, so grammy never puts it in allowed_updates; a heart reaction never reaches Claude. (Asked 2026-06-22.)
- **THE working tap-to-SEND = the plugin's NATIVE permission buttons.** When the session requests a permission-gated tool, the plugin posts **✅ Allow / ❌ Deny** (perm:* callback) and the tap WORKS (server.ts:731-785, routes via `mcp.notification` channel/permission). So route "send the draft" as a permission-gated action: user says "send it" → Telegram shows ✅ Allow/❌ Deny WITH the exact recipient+text → tap Allow → sent. One tap AND you see what you approve (the wrong-send safeguard, [[feedback_no_headless_fuzzy_send]]).
- NET: **tap-OPEN = URL button; tap-SEND = native ✅Allow/❌Deny permission prompt.** Custom callbacks / reply-keyboards / reactions all dead.
- **COROLLARY (user re-hit this 2026-07-18): NEVER use AskUserQuestion in a TG-channel session** — its option chips render in the chat but taps are swallowed (custom-callback path) and NOTHING reaches the session; to Claude it looks like the user never answered. Ask via numbered list + typed reply instead. **RESOLVED SAME DAY: the specific dead "✅ Yes, send it / ❌ No / More context / Open chat" bar the user kept tapping was a STALE REPLY KEYBOARD left by the retired sodanotif bot.js — wired to a bot that no longer listens. Cleared 2026-07-18 by sendMessage with reply_markup `{"remove_keyboard":true}` (msg 1077). If dead button bars ever reappear in the chat, that's the removal recipe.** Also: every Allow/Deny button dies when the plugin process that posted it restarts (pending perm ids are in-memory), and in auto-mode sessions the classifier resolves most calls silently so those buttons are rare anyway — typed replies ("dsend"/"go"/"1") are the reliable confirmation path.

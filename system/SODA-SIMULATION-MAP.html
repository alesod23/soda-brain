What it is, how it works

One laptop, one sandbox root per arm. A world agent writes each simulated day's events and the truth behind them; the runner moves a shifted clock to each event and drops it into JSON mailboxes and feed files; the live system's own code, copied fresh every day into a fake home, reads them through the same helpers it uses for real and writes to fake servers that copy the hub's and the CRM's routes; a simulated Alessandro answers the cards; at 23:40 a judge scores every event against the truth. Teal wires are the brain's paths (arm B and later).

One simulated day sim_day.run_day, about 45 min of wall time

The quick ticks run after every delivered event (the live tasks run every 5 to 15 minutes); the heavy pass every ~85 simulated minutes (the live sweep runs every 10). A day that raises is logged and the next day starts; the STOP file ends the run after the running day.

The alignment: is it a faithful test?

Each real component on the left of a pair, its stand-in on the right. A teal wire means the same code runs in the sandbox; a grey wire a stand-in that copies the behaviour; a dashed wire a stub that does one part of it; no wire means the sandbox does not have it. The pills on a real component are its maintenance surface: sched its own task, cron or service, store its own state or log, rules its own rule ledger.

Where the simulation is not the real system

The largest gap of night 3 is closed (G84, 4 Oct 20:40): every /review/* route of the sandbox intake now runs the sandbox copy of review-api.js and review-artifact.js (fakes/review_twin.js, one process per request under the sandbox clock and wall), so the producers' drafts attach to review items (kind waiting when the step is not due, CRM H56), the hub-card mirror and crm-outdated.js tick after every event, and the simulated him decides on the CRM review board (approve, skip, comment, then one commit that sends) besides the hub. The judge sees the review item and counts a committed approve as his yes. What is still not the real thing: /review/generate runs to the end and answers 200 (live: 202 and a polled job); "generate missing" is capped at 4 a pass and 12 a day (run.json review_gen_pass / review_gen_day; live he presses it with no cap); the board is read as JSON, not the review mode page; the sandbox has one CRM writer (live: the box writes, the laptop proxies); crm-outdated ticks after each event, not on a 10-minute clock; the box feedback session that files his sentences (feedback_session.py, the retired feedback_worker.py's successor) is not in the sandbox, only the review commit's own digest is.

The approaches tested

Night 3 asked one question: does the brain in the readers (and an Edge skill on top) raise the score and the currency of what he sees, without false closes, and at what cost. The arm is one switch in world/run.json, read by simenv.env() and build_sandbox.py; every arm sees the same world.

  • HUB_OUTDATED_BRAIN=0; todo_match.py is not copied, so the sweep's brain pass fails to import, as before 3 Oct
  • the meeting reader's MCP config is empty: no match_event tool
  • root ~/sim/arm-a, ports 43xx; ran 2 days (12 and 13 Oct)

B: the brain in the readers

  • todo_match.py copied, HUB_OUTDATED_BRAIN=1, a strong hit at 0.84 (MATCH_STRONG)
  • the fake door :4250; the CRM reader asks it over HTTP (crm-app/brain.js); the meeting reader has match_event (12 turns)

C: B plus Edge skill hints (built, not run)

  • edge_hints.py apply appends four Edge skill texts to the sandbox hints the readers already read, with a .simkeep so the build keeps them; zero extra calls
  • crm-reader: kiro-verify-completion; inbound-asks and due-today: inbox-manager; meeting-loop: meeting-action-extractor (texts in docs/edge/)

The eval

Every event of the day is scored 0 to 100 against the world's truth. Code measures what can be measured (was it seen, how fast, was anything sent without a yes); one Opus call per day judges the rest for all the day's events together; the simulated him adds one line a day on what he saw. A send without his yes zeroes the event.

The judge's path judge.judge_day, 23:40 simulated

event score = detected 20 + person 10 + timely 10 + step 30 x (0|1|2)/2 + artifacts 20 x (0|1|2)/2 + clean 10 = 0 when anything was sent to that person without his yes (FATAL) hub_surface = 100 x (1 - irrelevant views / all views), cards and Today rows, the day's passes of the simulated him day score = average of the day's event scores and its hub_surface line (days.jsonl, PROGRESS.md)

      How to keep it

      The rule

      • the harness and this map change in the same turn: a new fake, guard, arm, metric or switch is a row here, dated
      • the data is one JS block at the bottom of this file (NODES, SANDBOX, ALIGN, METRICS, RESULTS, REG); the charts draw themselves
      • the numbers of section 5 come from compare.py report and scores.jsonl, never from PROGRESS.md (it repeats the last score on a failed day)
      • no secrets, no tokens, no real person: the cast is fictional, at .example

      The review, before he sees it

      • python tools/review_map.py --html system/SODA-SIMULATION-MAP.html --out system/_review-sim --charts chart-sandbox,chart-align,ts --sections how,align,eval,results,registry --phone 390, run in ~/soda-brain (no inspect.py there)
      • RESULT: CLEAN in both themes, then a look at every screenshot (full page, each chart, 390 px): labels inside their shapes, wires that read right, nothing wider than its box

      How this page is kept. It sits next to SODA-SYSTEM-MAP.html in soda-brain/system/ and follows the same rules: dated, updated in the same turn as the harness, no secrets. It holds its own copy of the system map's chart engine (the lane chart with orthogonal wires in the gutters, the bus under the chart, chips for every other link) so the two pages change independently.

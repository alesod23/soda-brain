When I produce a self-contained text deliverable the user will paste somewhere outside the chat (application answers like YC/essays, form fields, bios, cover letters, outreach copy, captions, any "give me a version of X" draft), I MUST also push the final chosen text to the clipboard with `Set-Clipboard -Value @'...'@` (single-quoted here-string, closing `'@` at column 0). Don't make the user re-select and copy out of the chat.

**Why:** The user flagged (2026-05-26) that a YC application answer was NOT copied to clipboard even though it was clearly paste-bound text. My prior clipboard rules were too narrow — scoped only to WA drafts ([[feedback_wa_message_close_style]]) and HTML deliverables ([[feedback_html_deliverable_browser_url]]) — so a plain-text essay fell through the gap. The paste-destination pattern is identical regardless of medium.

**How to apply:** Treat clipboard push as part of delivering ANY pasteable draft, across all sessions. When I present multiple versions, copy the one the user converges on (or the latest/recommended single version). Confirm briefly that it's on the clipboard. This generalizes the two narrow rules; it does not replace their extra requirements (WA = clipboard + 🙌 close; HTML = clipboard + bare file:/// URL on its own line).

**SHELL commands the user must run → ALSO clipboard (added 2026-05-28):** Every time I hand the user an actual shell/terminal command to run (executable paths, `!`-prefixed in-session commands, re-login one-liners, anything they copy-paste into a terminal), push the exact command to the clipboard via `Set-Clipboard`. The user demanded this ("EVERY TIME YOU GIVE ME A COMMAND TO RUN COPY IT ON MY CLIPBOARD") after a command they had to hand-retype failed.

**SCOPE — clipboard SHELL commands ONLY, never `/slash` commands (clarified by user 2026-05-28):** Do NOT clipboard Claude Code slash commands (`/mcp`, `/daily`, `/triage`, `/dump`, etc.). Those are short things the user types into the Claude prompt themselves; copying them is noise (the user explicitly said "anything that is /something I can do myself"). The test: if it starts with `/` and is a Claude command → DON'T clipboard, just name it. If it's a real terminal command (executable + paths + flags, runs in bash or PowerShell) → DO clipboard it.

**Two-part rule for the shell commands:** (1) clipboard it, and (2) match syntax to the shell it runs in. The `!` prefix here routes to **bash** (`/usr/bin/bash`), NOT PowerShell — a `!` command must be bash syntax (no `&` call operator; forward-slash quoted paths like `"C:/Users/.../python.exe"`). A PowerShell `& "..."` line pasted after `!` errors with `syntax error near unexpected token '&'`. If meant for a separate PowerShell window, use PS syntax and say so.

**ROBUSTNESS — never use bare `Set-Clipboard`; it fails intermittently (added 2026-06-16):** `Set-Clipboard`/`Get-Clipboard` throw `System.Runtime.InteropServices.ExternalException` — *"Requested Clipboard operation did not succeed"* — whenever another process holds the Windows clipboard lock for an instant (clipboard managers, browsers, Obsidian, RDP). It is random and WILL recur. The user hit this 2026-06-16 (a register command silently failed to copy). **ALWAYS copy via the retry helper `~/.claude/scripts/set-clip.ps1`** (retries Set-Clipboard ~15× with backoff, verifies the round-trip, falls back to `clip.exe`; prints `CLIP_OK`/`CLIP_FAIL`). Usage: `& 'C:\Users\Alessandro\.claude\scripts\set-clip.ps1' -Text $cmd`. Only claim "copied" when it returns `CLIP_OK` (or `Get-Clipboard` confirms). A one-shot `Set-Clipboard` that throws = the copy did NOT happen; treat that as a failure, not done.

**OBVIOUS PASTE TARGETS I kept missing (added 2026-06-21):** Catchup/briefing prompts written for the user to paste into another Claude session are paste-bound text just like essays and form answers — clipboard them immediately on output. Same for: translation prompts, Lovable/AI-builder prompts, any multi-line block the user will clearly paste somewhere else. "Will the user paste this outside this chat?" — if yes, copy it. Don't wait to be told.

**COPY-INTENT IS STICKY ACROSS REVISIONS — every later version gets copied too (added 2026-06-26):** Once the user asks to "copy" / "copy to clipboard" a draft, that intent persists for the WHOLE iteration thread, not just the first output. Every subsequent revised/refined version of that same draft must be auto-copied via `set-clip.ps1` on output, WITHOUT being re-asked and WITHOUT ending the turn on a question like "want me to copy this?". The user caught me (2026-06-26) producing a revised email and asking whether to copy it instead of just copying — after the original ask had been "correct it and copy to clipboard." Rule: if the user ever signaled copy-intent for a deliverable, treat every iteration of that deliverable as copy-bound until they say stop. Offer tone tweaks AFTER copying, never as a gate before it.

**HARD ENFORCEMENT — never narrate an unexecuted clipboard action (added 2026-05-26):** The user caught me writing "it's on your clipboard" for a Lovable prompt I had NEVER actually copied — I described the action without running the tool. This is a verification/honesty failure, the exact thing the CLAUDE.md IRON LAW forbids. The fix is mechanical and absolute: the words "on your clipboard / copied / I've copied / pushed to clipboard" may ONLY appear in my reply if `Set-Clipboard` was actually invoked in THIS turn. After copying, verify with `Get-Clipboard -Raw` (check non-zero length + a known substring) before claiming success. If I'm about to type a clipboard/copied claim and there is no `Set-Clipboard` tool call in the current turn, STOP and run it first. Generalize: any claim of an action (copied, saved, sent, created, deployed) requires the actual tool call + fresh evidence in the same turn — telling the user it's done is a lie unless I did it and checked.

User rule (2026-07-19, after two bad experiences the same night): when the Telegram lane dies, do NOT spawn a new `claude --channels`/start-savior2 session automatically — not from a watchdog, not as a "fix". A respawned session has no context, competes for the bot token, confuses the user with error tabs, and "You're not capable of that. That shouldn't be the fixed solution."

**Why:** the first auto-spawn attempt created competing sessions + a token war; the second attempt failed with a wt quoting error tab in the user's face. Meanwhile the ACTUAL fix takes seconds and preserves context.

**How to apply:** TG-Savior-Watchdog stays ALERT-ONLY (phone push via sodanotif push.js): "lane offline → run /mcp in the savior terminal; if the session is truly gone, run start-savior2.ps1 manually." `/mcp` reconnect in the live savior session re-acquires the token (proven repeatedly). Only the USER decides to start a fresh savior. See [[reference_telegram_channel_plugin]].

**2026-09-01 — the savior moved to the DA VPS.** The ritual is now: user double-Ctrl+C's any laptop savior, then types `restore-savior` on the box (or `vpsc` from laptop PowerShell = ssh + restore-savior). `/usr/local/bin/restore-savior` on the box is ATTACH-OR-CREATE for tmux session `savior` running `claude --continue --channels plugin:telegram@claude-plugins-official` — running it twice re-attaches, so the never-respawn rule is structurally enforced; ssh dropping only detaches. Token+allowlist live at `/home/da/.claude/channels/telegram/` (v3 bot). The rule still holds for ME: never start/kill the savior tmux as a "fix"; alert and let him run restore-savior.

**2026-09-04 — the box savior had been DEAD since 2026-09-03 13:33** (its `claude` exited, tmux session gone, nothing restarted it; no reboot/OOM). User directive: "the vps should always have an active one", and several RC sessions are fine (RC is per session; only the Telegram poller must be unique). Now on the box: `~/.local/bin/box-sessions.sh` (cron `*/5`, log `~/box-sessions.log`) keeps TWO tmux sessions alive, attach-or-create, never respawning a live one: `savior` = `claude --name "savior box (dd-mm)" --remote-control ... --channels plugin:telegram@...` and `workbench` = RC only (phone playground, no bot token). It also answers the "trust this folder" prompt. `~/.local/bin/restore-savior` (user copy, first on PATH) runs it then attaches. This is the sanctioned exception to "never respawn": a FRESH savior after death is exactly the box ritual; the rule still forbids killing a live one or running a laptop savior alongside.

**2026-09-03 — the laptop/box token war, diagnosed and closed.** He kept running laptop `Restore-Savior` while the box savior was alive: same v3 token, two (then FOUR) `bun ... telegram/0.0.7` pollers on the laptop plus the box one. Telegram hands each update to whichever poller asks first, so a laptop session got 👀-reactions from one place, replies from another, and stale "hi" replays after `/mcp reconnect`; "connected plugin but receives nothing" = this, every time. Fix in `~/.claude/scripts/start-savior2.ps1`: (1) `Restore-Savior` now ssh-checks `tmux has-session -t savior` on the box and ATTACHES (= vpsc) when alive; a laptop savior starts only if the box is unreachable or with `-Local`; (2) laptop launch uses `claude --name "savior 3 (dd-MM)"` so the tab is titled without the `:sa` hotstring; (3) the `/mcp reconnect` keystroke injector is OFF by default (`-Reconnect` opts in). **Diagnostic when the lane "looks connected but is deaf": count pollers on BOTH machines** (`Get-CimInstance Win32_Process | ? CommandLine -like '*telegram/0.0.7*'` on the laptop, `pgrep -af telegram` on the box); more than one total = the bug.

**2026-09-07 re-attach loop.** The laptop tab attached to the box savior died with "client_loop: send disconnect: Connection reset" every time the laptop lost internet (phone hotspot off); the box savior itself was never affected (tmux keeps running). `vpsc` (PowerShell profile) and the attach path of `start-savior2.ps1` now loop: ssh exit 255 = dropped link -> wait until TCP 22 on 169.58.128.217 answers (`Test-BoxPort`) -> re-attach to the same tmux session; exit 0 (Ctrl+B D detach) ends the loop; Ctrl+C during the wait stops it. Never double-Ctrl+C inside the attached session: that reaches the savior claude.

**2026-09-08 wheel scrolling on the box.** Inside tmux the mouse wheel did nothing for Claude (only PgUp/PgDn): tmux `mouse on` hands wheel events to an app that runs in the alternate screen, and Claude Code does by default. Fix = the same env the laptop uses: `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1` on both exec lines of `~/.local/bin/box-sessions.sh` (output stays in the tmux pane history, wheel-up enters copy mode and scrolls), plus `set -g history-limit 20000` in `~/.tmux.conf`. Workbench restarted with it; the savior only picks it up at its next restart (never kill a live savior as a fix: his call).

**2026-09-08 public route outage.** At 13:11 the box public address 169.58.128.217 stopped answering the laptop (no ping, port 22 closed) while the box itself was fine and reachable over Tailscale (through a DERP relay). Result: every ssh to the public IP got "Connection reset", the attached savior tab died, and the coattio box server went to local mode because it could not probe the laptop either. Fix: ssh alias `box` now points at 100.85.52.84 (Tailscale), `box-public` keeps the old address; `vpsc` / `vps` use `Get-BoxRoute` (Tailscale first, public fallback, wait loop otherwise); `start-savior2.ps1`, `vault-git-sync.ps1` (root brain sync), `/tovps` and `/telegram-switch` were moved to the Tailscale address. Both routes are tested with `Test-BoxPort <ip>`.
